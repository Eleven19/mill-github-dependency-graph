# v0.3.0 — accurate manifests: module deps, dependency scopes, and a working run link

Two correctness fixes that change what your dependency graph says, plus the polish around them.

```yaml
mill-build:
  mvnDeps:
    - "io.eleven19.mill-github-dependency-graph::mill-github-dependency-graph_mill$MILL_BIN_PLATFORM:0.3.0"
```

Nothing here breaks a build. Two things change what gets submitted, so read the first two sections before upgrading a repository whose graph you watch closely.

## Fixed: dependencies from internal `moduleDeps` were missing

If `app` has `moduleDeps = Seq(lib)` and `lib` depends on Jackson, then anyone consuming `app` gets Jackson on their classpath. `app`'s manifest said otherwise.

This was found in this plugin's own graph. `plugin` depends on `report`, `report` depends on scalatags, and `plugin`'s manifest reported ten dependencies with scalatags absent — while the published `mill-github-dependency-graph_mill1_3` POM declares `github-dependency-graph-report_3`, which declares scalatags.

The practical cost: someone asking *"did `app` pick up the vulnerable Jackson?"* by reading `app`'s manifest was told no, when the answer was yes.

Those dependencies are now reported, marked **indirect** — the module did not declare them, but it does depend on them. The internal module itself is not reported: it is a module in your build, not a Maven coordinate, so it has no purl and cannot be a node.

> **What changes for you.** Manifests get larger, and modules with `moduleDeps` report dependencies they did not before. That is the correction. Every module's dependencies are repeated in the manifest of every module that depends on it, so a deep internal graph multiplies the submitted payload.
>
> If that costs more than the accuracy is worth, `--no-module-deps` restores the old behaviour, and a single module can opt out with `includeModuleDeps`.

## New: dependencies say whether they ship or only build

Every dependency now carries a scope GitHub understands.

| What it is | Reported as |
|---|---|
| An ordinary module's dependencies | `runtime` |
| Everything in a `TestModule`'s manifest | `development` |
| `compileMvnDeps` under `--scope all` | `development` |

The field existed in the API and was previously sent empty on every node, so nothing distinguished a production dependency from one that exists only to run tests. Test modules are the reason this matters on most builds: a test module is an ordinary module with its own manifest, and on a build like `finos/morphir-scala` that is 69 manifests out of 157.

A coordinate reachable both ways is reported as `runtime`. If a library is on the runtime classpath it ships, whatever else also pulls it in, and understating that is the failure worth avoiding.

## Fixed: `job.html_url` was never populated

The environment lookup for it had a literal `$` in the variable name, so it matched nothing and every snapshot this plugin has ever submitted went out with no link back to the Actions run that produced it.

## New: `--no-module-deps`, and per-module settings

`--no-module-deps` on all three commands leaves out dependencies reached through internal `moduleDeps`. It only turns inclusion off, never on — it exists as an escape hatch for payload size, and there is no reason to overrule a build that asked for less.

The per-module trait gains a matching setting and a better name:

```scala
import mill._, scalalib._
import io.eleven19.mill.github.dependency.graph.{GraphScope, DependencyGraphModule}

object server extends ScalaModule with DependencyGraphModule {
  override def dependencyGraphScope = Task { GraphScope.All }
  override def includeModuleDeps = Task { false }
}
```

> **`GraphScopeModule` still works.** It is deprecated and now means exactly `DependencyGraphModule`, which carries both settings. Builds written against `0.2.0` keep compiling; the old name described only one of the two things the trait holds.

## Improved: a bad `--scope` reads like a CLI error

It was validated inside the command and threw, so a typo reached you wrapped in a Java stack trace. mainargs validates it now, which also puts the valid values in `--help`:

```
Invalid argument --scope <scope> failed to parse
```

## Improved: smaller things

- **`--output` is checked before the work, not after.** Pointing it at an existing directory used to resolve every module first — minutes, and network I/O — then fail on an argument checkable in microseconds.
- **`generate` and `report` no longer say "submitting".** The selector summary read `submitting N of M modules` on two commands that never contact GitHub. It now reads `covering`.
- **Report rows show that they expand.** Module and coordinate rows opened on click with nothing to indicate it, which left half the report undiscoverable.

## Upgrading

Nothing to change. If you watch your graph closely, expect it to grow: modules with internal `moduleDeps` will report more, and every dependency now carries a scope where it previously carried none.

To keep `0.2.0`'s narrower manifests, add `--no-module-deps` to your workflow.

## Known limitations

- **The GitHub UI shows less than the plugin sends.** Many dependencies are not linked back to their repositories, some are linked wrongly, and information the plugin provides — direct versus indirect among it — is not displayed. Most of this is on the GitHub side; there is [some discussion here](https://github.com/orgs/community/discussions/19492).
