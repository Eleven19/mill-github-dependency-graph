# v0.2.0 — configurable scope, module selection, and an HTML report

Three new options, a new command, and a fix for a crash that hit any build with a runtime-scoped transitive dependency.

Nothing in this release is breaking. The coordinate is unchanged from `0.1.0`, and all three commands behave exactly as before when you pass no flags.

```yaml
mill-build:
  mvnDeps:
    - "io.eleven19.mill-github-dependency-graph::mill-github-dependency-graph_mill$MILL_BIN_PLATFORM:0.2.0"
```

## Fixed: `generate` crashed on runtime-scoped transitives (#12)

Any build with a dependency declared at `<scope>runtime</scope>` failed outright:

```
java.lang.RuntimeException: Cannot find org.junit.platform:junit-platform-suite-commons in reconciled versions
  io.eleven19.mill.github.dependency.graph.ModuleTrees.getNameFromTree$1$$anonfun$1(ModuleTrees.scala:44)
```

That is not a narrow case — runtime scope is where SLF4J bindings, JDBC drivers and much of the JUnit platform live.

The cause was the resolution and the dependency tree walking *different* Maven scopes. The resolution was rooted at the module's synthetic coursier project, which carries the `compile` configuration; the tree roots carried no configuration at all, which coursier defaults to `default(runtime)`. The tree therefore spanned nodes the resolution had never reconciled, and coursier throws on the first one it reaches.

Both sides now resolve at the same scope, computed in one place so they cannot drift apart. Reported by `finos/morphir-scala`, where the graph went from failing to 157 manifests and 3472 dependency nodes.

## New: `--scope` chooses how much of each module to report

A Maven dependency has a *scope* saying when it is needed. This flag picks how far down that list to go. Each value contains the one above it.

| `--scope` | Covers |
|---|---|
| `compile` | `mvnDeps` and their compile-scope transitives |
| `runtime` | the default; adds `runMvnDeps` and runtime-scope transitives |
| `all` | adds `compileMvnDeps`, which are provided scope |

```sh
./mill io.eleven19.mill.github.dependency.graph.Graph/submit --scope all
```

`--scope all` is new coverage rather than a preference: `compileMvnDeps` — Lombok, annotation processors, a servlet API your container supplies — were reported at **no** setting before this release. They ship in nobody's jar, but a vulnerability in one still runs on your build machine.

A single module can declare its own scope:

```scala
import mill._, scalalib._
import io.eleven19.mill.github.dependency.graph.{GraphScope, GraphScopeModule}

object server extends ScalaModule with GraphScopeModule {
  override def dependencyGraphScope = Task { GraphScope.All }
}
```

A `--scope` passed on the command line overrides every module's declaration, so it is not a no-op — it is how you force one scope across the whole build.

There is no `test` scope, and you are not missing one: Mill maps `test` to the same set as `runtime`. Your test modules are ordinary modules and get their own manifests.

## New: `--modules` and `--exclude-modules` choose which modules to cover

Both take [Mill selectors](https://mill-build.org/mill/cli/query-syntax.html) — the same syntax as any other Mill command — and both are repeatable.

```sh
./mill io.eleven19.mill.github.dependency.graph.Graph/submit \
  --exclude-modules '__.test'
```

Whenever a filter drops anything, the run says so: `submitting 3 of 5 modules, 2 excluded by selector`.

Two behaviours worth knowing before you pin a selector in CI:

- **A selector Mill cannot resolve is a hard error.** A job pinned to `--exclude-modules 'legacy.__'` starts failing the day the `legacy` module is deleted, rather than quietly submitting a graph that no longer matches your build.
- **Matching is literal on a selector's final segment.** `__.test` matches modules whose last segment is exactly `test`; it does not match `itest`, `tests` or `testing`. On `finos/morphir-scala` that is the difference between 96 manifests and 88.

**Selectors that leave nothing to report are refused.** GitHub keys each submission on a correlator that is stable per workflow and job, so an empty submission does not get ignored — it *replaces* your repository's dependency graph with nothing, and Dependabot goes quiet. Failing the build is much easier to notice.

## New: `Graph/report` renders the graph as HTML

```sh
./mill io.eleven19.mill.github.dependency.graph.Graph/report --output graph.html
```

One self-contained file — inline CSS and JS, no CDN, no asset folder. It opens from a `file://` URL, survives being emailed, and works as a CI artifact with no web server.

Two tabs:

- **By module** — module, direct, indirect, total. A row expands to that module's dependencies, each badged direct or indirect.
- **By dependency** — `org:name`, every version seen, how many modules carry it. A row expands to name those modules, and rows where one coordinate appears at more than one version are marked.

One filter box filters whichever tab is active.

The by-dependency tab answers a question the JSON cannot without a script: *which modules carry `slf4j`, and do they agree on a version?* That is why it exists — the README's old recipe for it was a `grep`.

A marked "version conflict" means one coordinate at more than one version **across modules**. Within a single module coursier has already reconciled to one version, so a conflict is always two modules resolving the same library differently. It is a statement of fact, not a judgement about risk.

`report` takes the same `--scope`, `--modules` and `--exclude-modules` flags, and the page states which scope and selection it was built from.

## New: `--output` on every command

```sh
./mill io.eleven19.mill.github.dependency.graph.Graph/generate --output manifests.json
```

On `generate` and `submit` it writes the manifests as JSON. On `report` it writes the HTML page. A relative path resolves against the workspace root, missing parent directories are created, and pointing it at an existing directory is an error rather than a guess.

On `generate` and `submit` this is an *extra* copy — Mill still writes its own `out/…/generate.json` either way. On `report` it replaces the default location.

If you want the manifests on stdout for `jq`, you do not need a flag — Mill already does it:

```sh
./mill show io.eleven19.mill.github.dependency.graph.Graph/generate | jq '...'
```

## New artifact

The HTML renderer lives in its own module so it can be tested without a Mill build harness. It has no Mill dependency and carries no platform suffix.

| | Group ID | Artifact ID |
|---|---|---|
| **Report** | `io.eleven19.mill-github-dependency-graph` | `github-dependency-graph-report_3` |

You do not need to add it — the plugin depends on it. It does mean the plugin now pulls scalatags transitively.

## Known limitations

- **`moduleDeps` land in the depended-on module's manifest, not the depending one** ([#16](https://github.com/Eleven19/mill-github-dependency-graph/issues/16)). If `app` depends on `lib` and `lib` brings in Jackson, Jackson appears under `lib`. Nothing is missing from the graph as a whole, but checking whether `app` pulled in a vulnerable library by reading `app`'s manifest will mislead you.
- **`job.html_url` is never populated** ([#15](https://github.com/Eleven19/mill-github-dependency-graph/issues/15)). The submitted snapshot loses its link back to the Actions run.
- **The report's expandable rows have no visual affordance** ([#23](https://github.com/Eleven19/mill-github-dependency-graph/issues/23)). Module and coordinate rows expand on click, but nothing indicates it.
- **`DependencyNode.scope` is always absent** ([#19](https://github.com/Eleven19/mill-github-dependency-graph/issues/19)). GitHub cannot distinguish a production dependency from a build-time one.
